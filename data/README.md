# Data Directory

Role and trait definitions used by the pipeline and analysis tools.
This extends Christina Lu's original dataset format with additional fields
and metadata. See [`data_analysis/`](../data_analysis/) for the scripts that
generate and process this data.

## Directory Structure

```
data/
├── goal_roles_and_traits.json   # Curated subsets of goal/nongoal roles and traits for experiments
├── combination_scores.json      # Sonnet incongruity scores for role+trait combos
├── extraction_questions.jsonl   # Questions used in pipeline Step 1
├── seed_queue.json              # Inventory and state of every candidate entity (Sep 2026 expansion; see below)
├── roles/
│   ├── role_list.json           # {stem: description}, GENERATED by tools/sync_entity_lists.py (337 roles, Sep 2026)
│   └── instructions/            # Per-role JSON files (338 files incl. default.json)
│       ├── <role>.json
│       └── ROLES_TO_ADD.md       # Candidate roles and role-side coverage notes
└── traits/
    ├── trait_list.json           # {stem: description}, GENERATED by tools/sync_entity_lists.py (659 traits, Sep 2026)
    ├── trait_antonyms_v4.json    # {name: {negative_label, antonym_score, reasoning}} (lags: 240 entries)
    ├── antonym_check_history.jsonl  # append-only: every antonym check's candidates and the instructions it read
    └── instructions/             # Per-trait JSON files (659 files; 262 pairs recorded in `arrangement`)
        ├── <trait>.json
        ├── TRAITS_TO_ADD.md      # Candidate traits and addition history
        └── NEG_REGENERATION_NOTES.md  # Traits with misaligned neg instructions
```

`role_list.json` and `trait_list.json` are **generated views** of the
instruction files (since 2026-09-07): `{stem: description}`, sorted by stem,
one entry per instruction file with a non-empty `description`
(`roles/instructions/default.json` has none and is skipped).  No code reads
them; they are a one-file index for humans and LLMs.  After adding or editing
an instruction file run `uv run python tools/sync_entity_lists.py`;
`--check` exits 1 while they lag, and `tools/tests/test_sync_entity_lists.py`
fails.  Never hand-edit them.

## Instruction File Format

### Roles (`roles/instructions/<role>.json`)

```json
{
  "description": "One-sentence description of the role",
  "instruction": [
    {"pos": "System prompt inducing the role"}
  ],
  "questions": ["Question 1", "..."],
  "eval_prompt": "Evaluation template with {question} and {answer} slots"
}
```

Role instructions have only `pos` variants (no neg/opposite).

### Traits (`traits/instructions/<trait>.json`)

```json
{
  "positive_label": "trait_name",
  "negative_label": "antonym_name",
  "description": "One-sentence description of the trait",
  "instruction": [
    {"pos": "System prompt inducing the trait",
     "neg": "System prompt inducing the opposite"}
  ],
  "questions": ["Question 1", "..."],
  "eval_prompt": "Evaluation template with {question} and {answer} slots",
  "source": "optional: instrument the trait was imported from (see below)"
}
```

The `positive_label`, `negative_label`, and `description` fields were added
to Christina Lu's original format (which had only `instruction`, `questions`,
and `eval_prompt`). The `eval_prompt` is derived from `description` via a
fixed template; see `regenerate_trait_instructions.py`. If you use Roger's prompt for instruction geration, the `negative_label` is also passed in, giving tigher clustering instructions, especially the neg instructions.

The three JSON files that sit *beside* the `instructions/` directories
(`roles/regeneration_usage.json`, `traits/regeneration_usage.json`,
`traits/antonym_check_usage.json`) are cumulative API token-usage records
written by the regenerate and antonym scripts, not corpus entries; they are
kept out of `instructions/` so nothing that globs the corpus reads them.  `traits/antonym_check_history.jsonl` sits there for the same reason: one JSON
object per antonym check, never rewritten, holding the candidates the
generator named and the instruction set it read (written by
`data_analysis/seed_entities.py`; see `AGENT_NOTES.md` § "Keep every sample").

**Labels vs file names.** `positive_label` is the canonical *display* form
of the trait name and may contain hyphens, spaces and capitals
(`systems-thinker`, `traditional (Inglehart-Welzel)`); the file stem is
derived from it by `assistant_axis.entity_id.normalize_to_file_name`
(lowercase, hyphens and spaces to `_`, parentheses dropped, diacritics
folded to ASCII).  The
reverse direction is lossy, so
anything that renders a trait name to a human should call
`assistant_axis.entity_id.corpus_display_name(stem)`, which reads
`positive_label` back from this directory.  Traits imported from a named
instrument use the label convention `<pole> (<Standard>)`, parentheses
dropped in the stem, and record the
instrument in the optional `source` field (the description itself does not
name it).  A second optional field, `tags` (a list of strings, e.g.
`["physical"]`), marks traits that belong to a separate research track
and must not be assumed part of the main cohort; see
`instructions/TRAITS_TO_ADD.md` § "Physical-attribute traits".  Both
fields are carried forward unchanged by the regenerate scripts and
ignored by the pipeline.  A third optional field, `generator`, is
written (and overwritten) by the regenerate scripts since September 2026
on both roles and traits: which script and prompt style produced the
instructions, a short hash of the template text, the model, temperature,
thinking budget and date.  Files without it predate that change.

**Seed queue.** `seed_queue.json` (Sep 2026) is the inventory of every
candidate entity in `traits/instructions/TRAITS_TO_ADD.md` and
`roles/instructions/ROLES_TO_ADD.md`, one entry per entity with its chunk,
pairing, partner, description drafts and notes, final description and
status; `data_analysis/seed_entities.py` reads and updates it.  The two
markdown files remain the record of the reasoning; the queue is the record
of state.  Entries whose file already existed when the queue was built
carry status `exists`.

**Arrangements.** Roles and traits may carry an `arrangement` field, an
object `{"kind": ..., "members": [...]}` (or a list of them) recording
which set of same-type entities the file belongs to and its shape:
`singleton`, `pair`, `triangle`, `square`, `octahedron`, `N-orthoplex`,
`N-cube`, `ring`, `tree`, `map`, `sequence`, `set`.  Members are file
stems including the entity itself.  A missing field means not yet
classified.  Validate with `uv run python data_analysis/check_arrangements.py`;
full rules in `AGENT_NOTES.md` § "The `arrangement` field".  Spelling is US English throughout (`honor`, `laborer`): the
corpus is LLM input and the generators write US English.  Full convention:
`AGENT_NOTES.md` § "Standard-derived trait labels".

## `goal_roles_and_traits.json`

Curated lists of roles and traits partitioned by goal content (as determined
by `data_analysis/classify_goals.py`). Each of `roles` and `traits` has:

- **`goal`**: All 5 instructions scored 2 (clearly describes a goal)
- **`non_goal`**: All 5 instructions scored 0 (clearly no goal)

Items are ordered by priority tiers (randomized within each tier):

| List | Tier 1 | Tier 2 | Tier 3 |
|---|---|---|---|
| `roles.goal` | 30 primary (varied) | 10 cluster duplicates | — |
| `roles.non_goal` | 30 most varied | 10 nice-to-haves | 30 most redundant |
| `traits.goal` | 30 max goal-space variation | 10 (mostly moral-circle-size spectrum) | 26 default-side of pairs / redundant |
| `traits.non_goal` | 30 max persona-property variation | 10 nice-to-haves | 17 pair partners / redundant |

For `traits.goal`, tier 1 prefers the less-HHH-default side of antonym pairs
(e.g., cruel over compassionate) and spans distinct ethical frameworks,
moral-circle extremes, and alignment-relevant anti-traits. Tier 2 holds the
remaining moral-circle-size entries (may be worth revisiting whether the spectrum
needs much finer resolution). Tier 3 holds the more default-like / redundant traits.

## `combination_scores.json`

Incongruity scores for all role+trait instruction combinations, generated by
`data_analysis/score_combinations.py` using Claude Sonnet. Each combination
gets one API call with all 5 index-matched instruction pairs scored
independently on a 0-3 scale (0 = fit well, 3 = very incongruous).

Structure: `metadata`, `scores[]` (per-combo with `per_pair` reasoning and
`score_min`/`score_max`/`score_mean`), and `summary` with distribution.

Default run covers all 40 goal roles x 40 non-goal traits + 40 non-goal
roles x 40 goal traits = 3200 combinations. Results show Sonnet interprets
incongruity more strictly than manual assessment: 51% score 0, 16% score 3.
The t_ combos (goal traits like harmful/lustful on professional roles) score
higher on average (mean 1.25) than r_ combos (communication-style traits on
character roles, mean 0.69).

## Notes Files

- **`TRAITS_TO_ADD.md`**: History of trait additions (moral circle spectrum,
  misalignment traits, RLHF triad, clean antonym pairs) and remaining
  candidates.

- **`ROLES_TO_ADD.md`** (in `roles/instructions/`): process for adding a
  role, the Sep 2026 demographic-coverage audit (role side), and candidate
  roles.  Companion to `TRAITS_TO_ADD.md`.

- **`NEG_REGENERATION_NOTES.md`**: Traits where the neg instructions don't
  match the corrected `negative_label` — typically due to RLHF influence
  during generation. Documents the misalignment, correct direction, and
  likely cause for each.
